# Сравнение способов запуска и проверки очистки

Цель проверки — найти самый лёгкий вариант, который **правильно** разбирает занятое место и запускается на обычных Linux-серверах и в Docker. Размер модели или успешный запуск команды сами по себе не считаются качеством решения.

## Условия сравнения

Для каждого варианта фиксируем версию кода, модель и её хэш, шаблон запроса, схему ответа, лимиты времени и контекста, число потоков, транспорт и права процесса. В сравниваемых прогонах меняется только заранее указанная часть: модель, способ вызова или состав передаваемых фактов. Отдельно записываем холодный запуск, повторный запрос, `memory.peak` всего контейнера или cgroup, OOM-события, занятое место на диске и размер релизного файла. Если есть только выборки RSS отдельных процессов, называем их выборками и не выдаём за общий пик.

Начальные контрольные случаи: том MySQL без установленного владельца и подтверждённой копии; PHP-сессии со сроком хранения 31 536 000 секунд; разрешённый просроченный QA-каталог, для которого допустим лишь предварительный план; production-медиа с незавершённым поиском ссылок; тайм-аут проверки открытых файлов; новый естественный случай, отсутствующий в прежних пробах. Проверяем итоговое решение, аргументы инструментов, существование каждой ссылки на доказательство и точный формат ответа. Транспортный сбой, ошибка схемы и смысловая ошибка учитываются отдельно.

Первичный порог качества для кандидата: ни одной рекомендации удалить объект с неизвестным владельцем, активным потребителем или неполной проверкой; правильная трактовка срока PHP-сессий; точный предварительный план для разрешённого QA-объекта; существующие идентификаторы доказательств; корректная схема во всех контрольных случаях. Прохождение шести случаев необходимо для дальнейшей проверки, но само по себе не доказывает надёжность на новых серверах. После изменения модели, запроса, схемы или окружения сравнение начинается заново.

Ресурсный порог для локального режима: полный путь с моделью работает в cgroup с лимитом 8 ГиБ и двумя CPU без OOM; после установки ему не требуются root, менеджер служб и внешний сетевой доступ; файл с включёнными весами помещается в ограничение GitHub Release в 2 ГиБ. Для принятия каждого окружения отдельно проверяем доступ к loopback, временный исполняемый каталог, видимость процессов и точки монтирования. Скрытый `/proc` или неизвестные потребители должны оставлять объект без удаления.

## Зафиксированная исходная точка

Этот документ содержит также исторические прогоны. В актуальном коде по состоянию на 25 сентября 2026 года `plan` использует схему-объект с ключом-кандидатом; результаты прежней формы-массива ниже не описывают текущие настройки.

Релиз `v0.1.0-preview` использует OpenCode CLI 1.14.21, временный `llama-server` b11160 и Qwen3.5-0.8B Q4_K_M. В одном запуске `plan` вернул только `unknown`, в другом после примерно 118 секунд ответ нарушил схему и содержал придуманные ссылки на доказательства. Проверка отклонила ответ без удаления. По выборкам RSS второго запуска сумма llama.cpp, OpenCode и Python составляла около 1,5 ГиБ; общего пика памяти для него нет. Точные результаты находятся в [протоколе модели](model-evaluation.md) и [трассе полного запуска](evidence/qwen35-0.8b-opencode-plan-e2e-20260924.json).

Рабочий контрольный путь `scan` → `manual-plan` → `apply` использует явно заданные правила и свежие проверки. Он полезен для оценки совместимости и защитных границ, но не подтверждает качество модельного `plan`.

## Варианты и статус

| Вариант | Что меняется | Качество решений | Память и время | Совместимость |
|---|---|---|---|---|
| OpenCode CLI + `llama-server`, 0.8B | Исходный релиз | Не прошёл проверку схемы и ссылок | В полном `plan` — около 118 секунд; короткий запрос занял 35,19 секунды. Выборочный RSS — 1 423 МиБ | Подтверждён Ubuntu 22.04 Docker для команд без модели |
| Прямой вызов `llama.cpp`, 0.8B | Убирается процесс OpenCode; CLI включает этот путь только через явный `--runtime llama` | Короткий JSON прошёл схему; модельное качество плана проверено отдельно ниже | Тот же короткий запрос занял 2,27 секунды; выборочный RSS дерева процессов — 901 МиБ | Проверен в отдельном сетевом пространстве с loopback; прогон был от UID 0 |
| Прямой вызов, динамический объект `items` | Исторический эксперимент формы ответа, где ключ `items` — разрешённый ID кандидата | 5 из 6 ответов прошли строгий разбор, один обрезал ID доказательства. Все шесть вернули `unknown`; модель пропустила допустимую рекомендацию `candidate_for_review` для QA-каталога | Два профиля по 6 случаев заняли около 73 секунд каждый; выборочный максимум RSS — 1 006 МиБ. CPU и общий cgroup-пик не измерены надёжно | Только локальный синтетический прогон, без подтверждения rootless и лимита 8 ГиБ |
| OpenCode CLI + другая малая модель | Меняются только веса и шаблон, если он необходим модели | Проверяется на одинаковых случаях | Проверяется под лимитом 8 ГиБ | Требуется проверка размера релиза |
| Движок Ollama или переносимый llamafile | Меняется движок модели при сохранении контракта плана | Нет сравнимого прогона | Нет сравнимого прогона | Требует отдельной проверки установки, loopback и временных файлов |

Короткий runtime-прогон использовал один запрос `Return exactly {"message":"ready"}` и одну JSON-схему при `ctx=4096`, двух потоках, модели с SHA-256 `bd258782e35f7f458f8aced1adc053e6e92e89bc735ba3be89d38a06121dc517` и llama.cpp b11160. Текст запроса совпадал, но OpenCode добавляет собственную системную инструкцию, которой нет у прямого вызова. Обе схемы приняли точный ответ. В отдельной диагностической записи OpenCode занял 35,19 секунды, включая 2,33 секунды до готовности `llama-server`; прямой вызов в прежнем парном прогоне занял 2,27 секунды всего. Выборочный RSS составил 1 423 МиБ и 901 МиБ соответственно.

Трасса объясняет большую часть паузы OpenCode после старта модели: сервер обработал два запроса. Первый обработал 565 входных токенов за 6,63 секунды и выдал 6 токенов за 0,44 секунды; второй обработал 2 019 входных токенов за 22,69 секунды и выдал 6 токенов за 0,44 секунды. Видимый поток OpenCode содержит только второй запрос (2 019 входных и 6 выходных токенов). Назначение дополнительного первого запроса не установлено: причина может быть в подготовке OpenCode, но трасса не доказывает конкретную функцию или плагин. В изолированном сетевом пространстве также видны четыре попытки DNS-разрешения `registry.npmjs.org` через локальный stub `127.0.0.53`; трасса не показывает соединений к внешнему адресу. Это подтверждает попытку DNS, а не отсутствие сетевых системных вызовов. Выборочный RSS измерялся с интервалом 0,5 секунды и не является `memory.peak`; прогоны выполнены от UID 0, поэтому не доказывают rootless-совместимость. Протоколы: [парное сравнение runtime](evidence/qwen35-0.8b-runtime-ab-20260924.json) и [диагностический прогон OpenCode](evidence/qwen35-0.8b-opencode-delay-diagnostic-20260925.json).

Профиль динамического объекта `items` сокращал ответы с пяти повторов одного кандидата до одной записи с ключом-ID. В шести baseline-случаях без подсказок имён и в шести случаях с ними результат одинаков по качеству: по одному ID доказательства был усечён, а разрешённый QA-объект остался `unknown`. Строгий разбор отклонил усечённый ID, не исправляя его. Текущий CLI по умолчанию использует схему-объект; прежний эксперимент доступен явно через `--schema-shape array`. Подробные входы, схемы и ответы сохранены отдельно: [без подсказок имён](evidence/qwen35-0.8b-object-schema-20260924.json), [с подсказками имён](evidence/qwen35-0.8b-object-schema-name-hints-20260924.json). Эти короткие прямые вызовы не заменяют полный тест `plan` через OpenCode и не подтверждают пригодность модели для очистки.

Итоговый выбор делаем только между вариантами, прошедшими качество и защитные проверки. Среди них предпочитаем вариант с меньшим пиком памяти, временем и числом условий для запуска. Если ни один не прошёл, модельный режим остаётся экспериментальным, а результат сравнения не называется готовой автоматической очисткой.
