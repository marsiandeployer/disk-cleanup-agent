# Проверенная совместимость

Проверка от 24 сентября 2026 года использовала опубликованный asset `v0.1.0-preview`, SHA-256 `be199f27857cda9a47bb1c8f5bce36476109a21f005333a1a99fa2968bb97bd3` (661 287 837 байт). Smoke запускался в официальных образах Docker без внешней сети, с закрытым PID namespace, лимитом памяти 8 ГиБ и UID 65534. Root filesystem был только для чтения; writable `HOME` монтировался отдельно.

«Поддерживается» здесь означает только проверенные команды управления диском и ручной план. Проверка не подтвердила качество или надёжность модельного `plan`; результаты модели описаны в [оценке моделей](model-evaluation.md). В smoke-прогоне модель вообще не запускалась.

## Контейнеры и видимость данных

В обоих поддерживаемых образах Docker настроил частный PID namespace. Для bind mount с тестовым файлом scanner сообщил частичную видимость процессов, а `apply` с явным точным одобрением завершился отказом `container_mount_process_visibility_unknown`. Тестовый файл и соседний control-файл сохранились.

Отдельная проверка создала 65 МиБ fixture внутри disposable container writable layer, не монтируя каталог данных с хоста. Точный `manual-plan` и `apply` удалили только fixture; control-файл сохранился. После проверки контейнер удалён. Это подтверждает только такой изолированный тестовый слой, не видимость процессов хоста и не безопасность очистки произвольных bind mount.

Утилита внутри контейнера видит только доступные ей `/proc`, mounts и файлы. Она не может делать вывод о процессах хоста по факту, что Docker daemon доступен или задан `--pid=host`. Для данных хоста запускайте утилиту на хосте, где есть нужная видимость. Никогда не монтируйте production-каталоги ради теста `apply`.

25 сентября 2026 года пересобран one-file asset из текущего дерева (661 315 038 байт; SHA-256 `9b6acd56ca1ce9d35c1d5276646599b8aacafd06588b605ce0cd4cd7a9efcc84`). Обновлённый `scripts/smoke-docker.sh` проверен на локальном Linux-хосте: Ubuntu 22.04, UID 65534, `--network=none`, лимит 8 ГиБ и два CPU. Контейнер читал корень реального хоста через read-only mount с пределом 100 объектов; отдельные fixture находились в одноразовом writable scratch. `doctor`, `scan`, `report` и `manual-plan` прошли, scratch остался без изменений, `apply` не запускался. В контейнере без Docker socket API учёт явно вернулся как `unknown`; на хосте текущий Docker API предоставил образы и тома, а размеры контейнерных слоёв и build cache остались `unknown`. Подробности и неуспешный запуск модельного `plan` записаны в [протоколе трёх проверок](evidence/docker-three-hypotheses-20260925.json) и [оценке модели](model-evaluation.md).

В контейнере также проверены `--network=none`, отсутствие Docker socket и CLI, а также `/tmp` как `noexec`; на Debian `/tmp` был read-only и `noexec`. `scan`, `report` и `manual-plan` завершились без сети. Опубликованный `v0.1.0-preview` предшествует добавлению учёта Docker usage. В исходном дереве отдельно проверен отказоустойчивый путь: `scan` и `report` при недоступном socket завершились со статусом Docker `unknown` и `deletion_performed=false`. Новая сборка из текущего дерева проверена отдельно выше.

## Память, диск и запуск

Сбор мусора и отчёты запускались под настроенным Docker memory limit 8 ГиБ, без OpenCode и без загрузки модели. `doctor` видел лимит 8 589 934 592 байта. Docker не предоставлял контейнеру cgroup `memory.peak`, поэтому общий пиковый RSS smoke не измерен. `ru_maxrss` отдельных Python-процессов был около 23 МиБ: Ubuntu 22.04 — doctor 23 760 КиБ, scan 23 284 КиБ, report 23 420 КиБ, manual-plan 23 468 КиБ; Debian 12 — 23 424, 23 160, 23 056 и 23 324 КиБ соответственно. Это отдельные значения; складывать их нельзя. Они не говорят о потреблении во время model inference.

На выделенном scratch filesystem первый запуск извлёк около 989,7 млн байт (943,8 МиБ) бандла. Сам asset занимает 630,7 МиБ. Если хранить исходный asset и уже распакованный кэш одновременно, в этих измерениях им требовалось примерно 1,54 ГиБ, без запаса на рабочие данные и логи. В disposable rootfs после smoke Docker показал writable-layer 978 299 975 байт; это включает кэш бандла и файлы проверки, а не только извлечённые данные. Повторный `--help` после распаковки занимал 0,92–1,11 секунды; первый занимал 13,5–14,7 секунды. Фактический минимальный свободный объём диска не определялся. Compatibility script требует не менее 4 ГиБ до pull образа, чтобы не расходовать общий диск во время QA; это предохранитель теста, не заявленный минимум продукта.

Исходный `install.sh` требует Python 3.10+ в системе и не устанавливает отдельный интерпретатор. По разложенным компонентам опубликованного asset постоянный объём файлов, которые он копирует (код, OpenCode, llama.cpp, GGUF и лицензии), оценивается в 726 622 208 байт (около 693 МиБ); wrapper и метаданные добавляют небольшой объём. Это расчёт по готовому бандлу без каталога `python`, а не отдельный запуск source installer. Скрипт установки перед загрузкой требует не менее 1 019 МиБ свободного места под GGUF и запас 512 МиБ; временные загрузки остальных компонентов могут увеличить пиковый объём.

Предыдущий 8-гигабайтный smoke подтверждал только лёгкие команды и ручной путь. Отдельный прогон 25 сентября запустил модель внутри лимита 8 ГиБ без OOM, но модельный `plan` не записался из-за неожиданной схемы ответа; cgroup `memory.peak` в среде не был доступен. Следовательно, успешный запуск inference сам по себе не подтверждает пригодность модели. Подробности — в [оценке моделей](model-evaluation.md) и [протоколе](evidence/docker-three-hypotheses-20260925.json).

## ARM64 и musl

Текущий сборочный скрипт жёстко ограничен `linux/amd64`; llama.cpp закреплён на архиве Ubuntu x64, OpenCode и Python — на x86_64. В официальных релизах OpenCode 1.14.21 перечислены Linux arm64 и musl варианты, а в llama.cpp b11160 — Ubuntu arm64 CPU. Это показывает, что варианты компонентов существуют, но не делает текущий единый asset совместимым: для ARM64 нужна отдельная сборка и проверка всех частей вместе. Для musl текущая связка не собрана и не проверена; Alpine-тест подтвердил отказ. Сборка llama.cpp из исходников и перенос Python runtime на musl в этой работе не проверялись. [Релиз OpenCode 1.14.21](https://github.com/anomalyco/opencode/releases/tag/v1.14.21), [релиз llama.cpp b11160](https://github.com/ggml-org/llama.cpp/releases/tag/b11160).

## Как повторить

Скрипт намеренно отказывается работать с Docker-контекстом `default`, текущим контекстом, его endpoint или Engine с совпадающим ID. Для запуска нужен отдельный тестовый Docker Engine с локальным Unix-сокетом и не менее 4 ГиБ свободного места на каталоге данных Docker и каталоге asset. Удалённые TCP/SSH-контексты не поддерживаются: локальная проверка диска не показывает свободное место удалённого узла.

Сначала прочитайте ID только у заведомо отдельного тестового Engine. Подставьте это значение вместо `TEST_ENGINE_ID` в команду `--dry-run`; она не создаёт контейнеры и не загружает образы:

```sh
docker --context dca-test info --format '{{.ID}}'
scripts/compat-smoke.sh --context dca-test --confirm-daemon-id TEST_ENGINE_ID --dry-run /path/to/disk-cleanup-agent-linux-x86_64
```

Сверьте выведенные ID, endpoint и DockerRootDir с тестовой машиной. Для полного прогона повторите команду без `--dry-run`. Скрипт проверит sidecar SHA-256, загрузит только недостающие тестовые образы, ограничит каждый Docker-вызов по времени, создаст помеченные тестовые контейнеры без внешней сети и применит `apply` только к fixture внутри disposable container rootfs. Он удаляет только свои контейнеры и скачанные им образы, если их ID не изменился и ими не пользуется другой контейнер. Не подключайте каталог данных хоста к smoke-контейнеру.
