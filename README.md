# Disk Cleanup Agent (preview)

Утилита обследует занятое место и собирает проверяемые сведения о крупных файлах и каталогах. Команда `plan` передаёт их локальной модели через OpenCode CLI; этот режим пока экспериментальный. Для заранее известных временных категорий есть отдельный `manual-plan`, которому модель не нужна. Удаление требует точного правила или одобрения пути и повторной проверки объекта непосредственно перед действием.

Первый выпуск рассчитан на Linux x86_64 с glibc 2.34 или новее. OpenCode и модель запускаются временными процессами от текущего пользователя. Root, PM2 и systemd не нужны. Для локального обмена между процессами нужен loopback. Проверка всего комплекта на машине с 8 ГБ ОЗУ ещё не завершена.

## Установка из GitHub

```sh
git clone https://github.com/marsiandeployer/disk-cleanup-agent.git
cd disk-cleanup-agent
sh scripts/install.sh --prefix "$HOME/.local/disk-cleanup-agent"
```

Установка из исходников использует системный Python 3.10 или новее. Установщик кладёт файлы в каталог пользователя. Он проверяет контрольные суммы закреплённых версий OpenCode, CPU-сборки llama.cpp и квантованной модели. Сеть нужна при установке. Для запуска без внешнего доступа используйте песочницу, оставляющую доступным loopback. Можно также скачать один исполняемый файл `disk-cleanup-agent-linux-x86_64` из GitHub Releases: он содержит интерпретатор Python, OpenCode, модель и необходимые библиотеки. GitHub Actions собирает его по тегу версии и публикует контрольную сумму.

## Использование

```sh
disk-cleanup-agent doctor
disk-cleanup-agent scan /path/to/check --output scan.json
disk-cleanup-agent report scan.json
disk-cleanup-agent plan scan.json --output plan.json
```

`scan` ограничивает число обследуемых объектов и явно отмечает неполный обход. `plan` запрашивает у модели дополнительные проверки для выбранных объектов и сохраняет основания и неизвестные обстоятельства только при корректном ответе. При ошибке модели план не создаётся. Снимки содержат пути и метаданные: храните их как служебные файлы, не публикуйте без проверки.

По умолчанию удаление выключено. Чтобы разрешить повторяющуюся категорию, создайте свой `consent.json` с точным родительским каталогом, именем или достаточно узким префиксом, UID владельца, минимальным возрастом и пределами удаления. Пример ниже ничего не разрешает, пока список `enabled_categories` пуст:

```json
{
  "enabled_categories": [],
  "category_rules": [
    {
      "id": "my-qa-screenshots",
      "parent_dir": "/path/to/qa-output",
      "basename_prefix": "screenshots-run-",
      "owner_uid": 1000,
      "min_age_seconds": 604800,
      "max_bytes": 2147483648,
      "max_count": 10,
      "required_consumer_checks": ["processes", "mounts"]
    }
  ],
  "approved_paths": []
}
```

В примере дополнительные проверки Docker, PM2, systemd, cron, Git и кода не являются обязательными для этого заведомо временного QA-каталога. Их отсутствие всё равно отражается в отчёте. Если поле `required_consumer_checks` не задано, перед удалением потребуются все проверки. После проверки владельца и назначения объекта включите категорию в `enabled_categories`. Затем создайте план по конфигурации и отдельно запустите удаление:

```sh
disk-cleanup-agent manual-plan scan.json --config consent.json --output plan.json
disk-cleanup-agent apply plan.json --config consent.json --approve-category my-qa-screenshots
```

`manual-plan` показывает совпавшие объекты как «настроены для проверки». Он не утверждает, что их можно удалить, и не запускает модель. Ошибочный ответ `plan` не переключает утилиту в этот режим автоматически.

Модель не может включить правило и не выполняет команд удаления. Смена файла, активный потребитель, точка монтирования, ссылка или недоступная проверка останавливают удаление. Крупный размер и отсутствие видимых процессов сами по себе не означают, что файл не нужен.

Повторная проверка перед удалением сокращает окно гонки, но не даёт атомарной гарантии, если другой процесс одновременно создаёт или открывает файлы. Для активно записываемого каталога сначала остановите его производитель штатным способом.

## Ограничения первой версии

- Qwen3.5-0.8B Q4_K_M остаётся пробной моделью. В одном раннем запуске с заданной схемой OpenCode она вернула допустимый план со статусом `unknown` для всех объектов. Последний прогон `plan` на двух кандидатах завершился примерно за 118 секунд ошибкой строгой проверки: модель пропустила обязательные поля `inspect_refs` и `limitations` и указала несуществующие ссылки на доказательства. Файл плана не создан, удалений не было. Qwen3.5-2B также не прошла проверку схемы и фактов; сравнение моделей приведено в [протоколе](docs/model-evaluation.md). Считайте `plan` экспериментальным режимом. Проверенный путь для настроенных правил — `manual-plan`, затем отдельный `apply` с явным одобрением.
- Песочница может скрывать процессы, контейнеры и соседние каталоги. Такие проверки отмечаются как неизвестные; утилита не считает отсутствие доступа доказательством отсутствия потребителей.
- В контейнере с распространёнными признаками Docker/OCI (overlay/fuse-overlayfs для `/` либо `/.dockerenv` или `/run/.containerenv`) проверка процессов для пути под отдельной точкой монтирования считается неизвестной. Это не универсальное обнаружение контейнеров: для проверки данных, смонтированных с хоста, запускайте утилиту на хосте. `--pid=host` сам по себе не подтверждает видимость всех процессов.
- Встроенный файл распаковывает исполняемые компоненты во временный каталог. Нужен каталог с правом записи и исполнения: при `noexec` он пробует другой доступный каталог, а для явного выбора используйте `DISKCLEANUP_RUNTIME_DIR`.
- Даже с отключёнными обновлениями OpenCode 1.14.21 в исследовательском запуске пытался выполнить DNS-запросы к GitHub и npm. Во внешне изолированной сети они не прошли; доступ к loopback для модели нужен.
- Автоматическое расписание не устанавливается. Утилиту можно запускать своим планировщиком после проверки правила и ограничений среды.

## Разработка и релиз

```sh
python3 -m unittest discover -s tests -v
python3 -m cleanup_agent.cli doctor
```

GitHub Actions запускает проверки при push и pull request. Тег `v*` запускает сборку одного файла, проверку его размера и публикацию в Releases. Для исходной установки и сборки релиза используются закреплённые версии зависимостей и контрольные суммы; веса модели не хранятся в Git.

OpenCode 1.14.21: [исходники](https://github.com/anomalyco/opencode/tree/v1.14.21). llama.cpp b11160: [релиз](https://github.com/ggml-org/llama.cpp/releases/tag/b11160). Квантование: [unsloth/Qwen3.5-0.8B-GGUF](https://huggingface.co/unsloth/Qwen3.5-0.8B-GGUF/tree/6ab461498e2023f6e3c1baea90a8f0fe38ab64d0). Исходная модель [Qwen3.5-0.8B](https://huggingface.co/Qwen/Qwen3.5-0.8B) распространяется по Apache-2.0.
