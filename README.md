# Disk Cleanup Agent (preview)

Утилита обследует занятое место и собирает проверяемые сведения о крупных файлах и каталогах. Команда `plan` передаёт их локальной модели через OpenCode CLI; этот режим пока экспериментальный. Для заранее известных временных категорий есть отдельный `manual-plan`, которому модель не нужна. Удаление требует точного правила или одобрения пути и повторной проверки объекта непосредственно перед действием.

Первый выпуск рассчитан на Linux x86_64 с glibc 2.34 или новее. OpenCode и модель запускаются временными процессами от текущего пользователя. Root, PM2 и systemd не нужны. Для локального обмена между процессами нужен loopback. Проверка всего комплекта на машине с 8 ГБ ОЗУ ещё не завершена.

## Установка из GitHub

```sh
git clone https://github.com/marsiandeployer/disk-cleanup-agent.git
cd disk-cleanup-agent
sh scripts/install.sh --prefix "$HOME/.local/disk-cleanup-agent"
```

Установка из исходников использует системный Python 3.10 или новее. Установщик кладёт файлы в каталог пользователя. При обновлении он сохраняет текущую и предыдущую версии для отката. Более ранние каталоги удаляются после переключения, если их исполняемые файлы не используются работающими процессами; без доступа к таблице процессов установщик оставляет старые версии. Он проверяет контрольные суммы закреплённых версий OpenCode, CPU-сборки llama.cpp и квантованной модели. Сеть нужна при установке. Для запуска без внешнего доступа используйте песочницу, оставляющую доступным loopback. Можно также скачать один исполняемый файл `disk-cleanup-agent-linux-x86_64` из GitHub Releases: он содержит интерпретатор Python, OpenCode, модель и необходимые библиотеки. GitHub Actions собирает его по тегу версии и публикует контрольную сумму.

## Использование

```sh
disk-cleanup-agent doctor
disk-cleanup-agent scan /path/to/check --output scan.json
disk-cleanup-agent report scan.json
disk-cleanup-agent plan scan.json --output plan.json
```

`scan` ограничивает число обследуемых объектов и явно отмечает неполный обход. `plan` передаёт модели до пяти крупнейших кандидатов, требует отдельную оценку для каждого и сохраняет основания и неизвестные обстоятельства только при корректном ответе. По умолчанию используется объектная JSON-схема и контекст 8192 токена. План модели носит справочный характер; неизвестные данные не разрешают удаление. При ошибке проверки ответа план не создаётся. Снимки содержат пути и метаданные: храните их как служебные файлы, не публикуйте без проверки.

В снимках `scan` и отчётах `report` секция `storage.docker` отдельно показывает размеры образов, записываемых слоёв контейнеров и томов по данным Docker Engine. Полную сводку BuildKit Engine сохраняет как основной источник. Если её нет или она неполная, для контекста `default` утилита проверяет `docker buildx ls` и вызывает read-only `docker buildx du --format=json` только когда он однозначно указывает на один работающий локальный builder с драйвером Docker. Тогда успешный пустой вывод означает отсутствие записей кеша. Отсутствующий Buildx, другой builder, ошибка, превышение лимита или неполный JSON оставляют кеш `unknown`; установка и создание builder-а не выполняются. Такие ошибки не останавливают файловое сканирование. Путь `DockerRootDir` относится к Engine; чтобы отдельно измерить каталог, доступный на этом сервере, используйте `du -xsh -- <DockerRootDir>`.

Docker показывает `Size`, `SharedSize` и `UniqueSize` образов отдельно: `Size` виртуальный и включает разделяемые слои. Сводные категории не складываются в общий итог, а виртуальные размеры образов нельзя складывать между собой. Для ручной сверки используйте `docker system df -v`; эта команда обходит файлы всех образов, контейнеров и томов и может занять время.

`plan` передаёт модели не более пяти обезличенных записей Docker отдельно от файловых кандидатов. В плане это отдельный раздел `docker_review`; он не участвует в `apply`. Предложить человеку проверить можно только запись кеша сборки, для которой собранные факты содержат `Reclaimable=true`, `Shared=false` и `Mutable=false`. Эти поля не подтверждают безопасность удаления. Образы, контейнеры и тома остаются `keep` или `unknown`, поскольку одной статистики размера недостаточно для вывода об их назначении. Это ограничение передачи и оценки; проверка модели на живых Docker-данных ещё не проведена.

По умолчанию удаление выключено. Чтобы разрешить повторяющуюся категорию, создайте свой `consent.json` с точным родительским каталогом, именем или достаточно узким префиксом, UID владельца, минимальным возрастом и пределами удаления. Пример ниже ничего не разрешает, пока список `enabled_categories` пуст:

```json
{
  "enabled_categories": [],
  "category_rules": [
    {
      "id": "my-qa-screenshots",
      "parent_dir": "/path/to/qa-output",
      "basename_prefix": "screenshots-run-",
      "owner_uid": 1000,
      "min_age_seconds": 604800,
      "max_bytes": 2147483648,
      "max_count": 10,
      "required_consumer_checks": ["processes", "mounts"]
    }
  ],
  "approved_paths": []
}
```

В примере проверки Docker, PM2, systemd, cron, Git, кода и настроек MySQL, PHP и Nginx не являются обязательными для этого заведомо временного QA-каталога. Их отсутствие всё равно отражается в отчёте. Если поле `required_consumer_checks` не задано, перед удалением потребуются все проверки. После проверки владельца и назначения объекта включите категорию в `enabled_categories`. Затем создайте план по конфигурации и отдельно запустите удаление:

Проверка настроек читает до 256 файлов и 2 МиБ за 5 секунд в `/etc/mysql`, `/etc/php` и `/etc/nginx`. Она ищет буквальные пути в `datadir`, `session.save_path`, `root` и `alias`. Переменные, недоступные файлы, превышение лимита и неполные или выходящие за эти каталоги `include` дают статус `unknown`. Если сервисных каталогов нет, проверка помечается как `not_applicable`. Точные пути файлов настроек остаются в локальном плане; в контекст модели передаются только статус и счётчики.

```sh
disk-cleanup-agent manual-plan scan.json --config consent.json --output plan.json
```

Перед `apply` создайте резервную копию через панель хостинга. Утилита не создаёт и не проверяет её: доступ к панели находится вне процесса очистки.

```sh
disk-cleanup-agent apply plan.json --config consent.json --approve-category my-qa-screenshots
```

`manual-plan` показывает совпавшие объекты как «настроены для проверки». Он не утверждает, что их можно удалить, и не запускает модель. Ошибочный ответ `plan` не переключает утилиту в этот режим автоматически.

Модель не может включить правило и не выполняет команд удаления. Смена файла, активный потребитель, точка монтирования, ссылка или недоступная проверка останавливают удаление. Крупный размер и отсутствие видимых процессов сами по себе не означают, что файл не нужен.

Повторная проверка перед удалением сокращает окно гонки, но не даёт атомарной гарантии, если другой процесс одновременно создаёт или открывает файлы. Для активно записываемого каталога сначала остановите его производитель штатным способом.

## Ограничения первой версии

- Qwen3.5-0.8B Q4_K_M остаётся экспериментальной моделью. В последнем однокандидатном E2E-запуске OpenCode в Docker (8 ГиБ, Ubuntu 22.04, UID 65534, без сети) скан прошёл, но модель сослалась на повторяющиеся или отсутствующие ссылки на доказательства; строгая проверка отклонила ответ и план не записала. После этого формат ответа упростили: модель возвращает оценку, а CLI сам добавляет ссылки на локальные доказательства. Исправленный формат проверен тестами и Docker smoke, но модельный запрос повторно не запускался, поэтому его полезность не подтверждена. В предыдущем запуске с QA/cache-файлом, MySQL и PHP-сессией модель вернула `unknown` для всех трёх. Полезных рекомендаций пока нет, цель получить больше полезных предложений, чем ошибочных, не достигнута. Qwen3.5-0.8B нельзя использовать как самостоятельный разборщик мусора. Ранее Qwen3.5-2B предлагала массово удалить PHP-сессии, а Qwen3.5-4B — удалить том MySQL без известного владельца и подтверждённой копии. [Протокол оценки](docs/model-evaluation.md) содержит детали.
- В испытаниях Qwen3.5-2B рекомендовала массово удалить PHP-сессии, а Qwen3.5-4B — удалить том MySQL, хотя его владелец и наличие резервной копии оставались неизвестны. Это реальные ошибки рекомендаций, не разрешение на удаление. Не принимайте вывод модели за доказательство безопасности или наличия резервной копии: перед `apply` проверьте назначение данных и сделайте резервную копию через панель хостинга. Утилита не проверяет копию автоматически.
- Песочница может скрывать процессы, контейнеры и соседние каталоги. Такие проверки отмечаются как неизвестные; утилита не считает отсутствие доступа доказательством отсутствия потребителей.
- В контейнере с распространёнными признаками Docker/OCI (overlay/fuse-overlayfs для `/` либо `/.dockerenv` или `/run/.containerenv`) проверка процессов для пути под отдельной точкой монтирования считается неизвестной. Это не универсальное обнаружение контейнеров: для проверки данных, смонтированных с хоста, запускайте утилиту на хосте. `--pid=host` сам по себе не подтверждает видимость всех процессов.
- Встроенный файл распаковывает исполняемые компоненты во временный каталог. Нужен каталог с правом записи и исполнения: при `noexec` он пробует другой доступный каталог, а для явного выбора используйте `DISKCLEANUP_RUNTIME_DIR`.
- Даже с отключёнными обновлениями OpenCode 1.14.21 в исследовательском запуске пытался выполнить DNS-запросы к GitHub и npm. Во внешне изолированной сети они не прошли; доступ к loopback для модели нужен.
- Автоматическое расписание не устанавливается. Утилиту можно запускать своим планировщиком после проверки правила и ограничений среды.

## Разработка и релиз

```sh
python3 -m unittest discover -s tests -v
python3 -m cleanup_agent.cli doctor
```

GitHub Actions запускает проверки при push и pull request. Тег `v*` запускает сборку одного файла, проверку его размера и публикацию в Releases. Для исходной установки и сборки релиза используются закреплённые версии зависимостей и контрольные суммы; веса модели не хранятся в Git.

OpenCode 1.14.21: [исходники](https://github.com/anomalyco/opencode/tree/v1.14.21). llama.cpp b11160: [релиз](https://github.com/ggml-org/llama.cpp/releases/tag/b11160). Квантование: [unsloth/Qwen3.5-0.8B-GGUF](https://huggingface.co/unsloth/Qwen3.5-0.8B-GGUF/tree/6ab461498e2023f6e3c1baea90a8f0fe38ab64d0). Исходная модель [Qwen3.5-0.8B](https://huggingface.co/Qwen/Qwen3.5-0.8B) распространяется по Apache-2.0.

Код этой утилиты распространяется по [MIT](LICENSE). Сторонние компоненты сохраняют свои лицензии; их тексты находятся внутри единого файла в каталоге `licenses` после распаковки.
